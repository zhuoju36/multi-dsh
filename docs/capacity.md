# 一期容量与硬件

结论先行：**≤10 用户，推荐 16 vCPU / 32 GiB / 500 GB NVMe 单机**；最低 8 vCPU / 16 GiB / 250 GB SSD（并发重任务 ≤3 个）。

以下是 2026-11-13 在参考机（16 vCPU / 32 GiB / 1 TB，DSH 0.2.1-rc.3）上的实测值，不是估算。

## 1. 实测数据

| 项目 | 实测值 | 测量方式 |
|---|---|---|
| DSH Web 进程常驻内存 | **313–315 MB** | 3 个实例并发，RSS 315 / 311 / 313 MB |
| gateway 进程常驻内存 | **62 MB** | 空载 + 若干请求后基本不变 |
| 每用户空载合计 | **≈ 375 MB** | DSH + gateway |
| 首页加载对内存影响 | +0.7 MB | 加载 39 KB 首页后 |
| 冷启动到监听 | **3.55 s** | 空 DSH_HOME（首次初始化 profile） |
| 温启动到监听 | **3.31 s** | 同一 DSH_HOME 重启 |
| 启动 CPU 峰值 | ≈ 1 核 × 4 s | 启动窗口平均 87% × 6 s |
| 空载 CPU | ~0% | `top` 采样 |
| 新建 DSH_HOME 体积 | **44 KB**（7 文件） | 无用户数据时；in-box bundle 不复制依赖 |
| 镜像源体积（checkout） | **2.9 GB** | node_modules 2.1 GB、前端 dist 22 MB |
| 10 实例空载合计 | **≈ 3.7 GB** | 375 MB × 10 |

关键结论：**空载很轻，内存风险来自单个用户的活跃会话**（工具输出、附件、构建/测试类命令），而不是实例数量本身。

## 2. 单用户资源建议

| 资源 | request | limit | 依据 |
|---|---|---|---|
| CPU | 0.5 vCPU | 2 vCPU | 空载≈0；启动/构建是瞬时峰值 |
| 内存 | 1 GiB | 2 GiB | 空载 375 MB；2 GiB 留出工具与附件的余量 |
| 卷 | — | 20 GiB | 新库 44 KB；增长来自会话、附件、projects |

> 若用户确实需要跑重构建（`pnpm build` 级），把 limit 提到 4 GiB，并把主机内存相应加到 64 GiB——不要在 32 GiB 主机上叠加 10 × 4 GiB。

## 3. 主机整体

### 推荐配置（10 用户）

| 部件 | 规格 | 计算 |
|---|---|---|
| CPU | 16 vCPU | 10 × 0.5 request = 5；并行重任务峰值约 8–10 |
| 内存 | 32 GiB | 10 × 2 limit = 20 + 平台 ~4 + OS/缓存 ~8 |
| 磁盘 | 500 GB NVMe | 见下 |
| 网络 | 50 Mbps+ 出网 | 主要是模型 API 与工具抓取，流量很小 |

平台组件开销（估算，非实测）：PostgreSQL 0.5 GiB、auth 0.1 GiB、llm-gateway 0.15 GiB、Docker 0.3 GiB、OS 1 GiB。

### 磁盘分解（10 用户）

| 项 | 容量 |
|---|---|
| OS + Docker | 50 GB |
| 镜像（3 GB × 3 个版本，共享层） | ~10 GB |
| 用户卷（10 × 20 GB） | 200 GB |
| 本地备份暂存 | 100 GB |
| 余量 | ~140 GB |

最低可用：**8 vCPU / 16 GiB / 250 GB SSD**（并发重任务 ≤3 个，用户卷 10 GB/人，备份直传 S3 不落本地）。

### 成本量级

按公有云通用型实例估算：16C32G ≈ 1–1.5 元/小时量级（按需），包月更省；500 GB NVMe 另计。一期 10 用户的硬件成本主要在**常驻内存**与**卷**，CPU 大部分时间空闲。

## 4. 扩展到 100 用户的换算（二期）

实测空载 375 MB/人 → 100 人全在线约 37.5 GB 内存、CPU 请求 50 核。但更现实的假设是活跃率：

- 10% 同时活跃：10 × 2 GiB 峰值 + 90 × 0.4 GiB 空载 ≈ 56 GiB → 3 台 32 GiB 节点；
- 30% 同时活跃：≈ 76 GiB → 4–5 台；
- 建议二期先做**空闲挂起**，把常驻实例压到活跃集合，再按活跃峰值 +30% 规划。

## 5. 尚未验证的部分（需要 soak test）

以下未实测，因为需要真实模型 key 与真实工作负载：

1. 单个用户跑一次完整对话（含工具调用、文件读写）时的内存峰值；
2. 10 个实例连续运行 24 h 的 RSS 漂移与文件句柄；
3. 大附件（DSH 默认 200 MiB 图片/300 MiB 请求体）对内存的瞬时抬升；
4. 冷启动在镜像未缓存节点上的耗时（预计拉 3 GB 镜像 30–60 s）。

建议在 auth + Compose 就绪后做一次 24 h soak：10 个实例、每 10 分钟一次页面加载、每实例每天 3 次真实对话，记录 RSS 曲线与启动耗时。达标线：单实例 RSS ≤ 1 GiB（P95）、10 实例合计 ≤ 8 GiB、启动 P95 ≤ 6 s。

## 6. 测量复现

```sh
cd /path/to/deepseek-harness
DSH_HOME=/tmp/measure-home node apps/cli/lib/bin.js --profile web --host 127.0.0.1 --port 3096 --no-open
ps -o pid,rss,vsz,pcpu,etime -p <pid>     # 常驻内存
ss -lnt | grep 3096                        # 监听耗时
du -sh /tmp/measure-home                   # 空库体积
```
